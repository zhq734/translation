## 修复：macOS 打开应用后设置页与 Dock 图标自动消失

- 现象：启动应用（`showDockIcon: true`）后设置窗口与 Dock 图标一起消失，再次打开设置页恢复正常。
- 根因：Electron `win.setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })` 在 macOS 默认会做
  `UIElementApplication ↔ ForegroundApplication` 进程类型转换，**每次调用都会隐藏窗口与 Dock 图标**
  （见 electron.d.ts 中 `VisibleOnAllWorkspacesOptions.skipTransformProcessType` 的说明）。
  `createSelectionButton` / `createPopup` / OCR 覆盖窗口 / 截图提示窗口在启动及划词过程中创建时各触发一次；
  而 Dock 呈现规则改为「仅设置窗口存在时显示图标」后，只有设置窗口开合才会恢复图标，因此图标不会自己回来。
- 修复：新增 `src/main/windowWorkspaceVisibility.ts` 导出 `ALL_WORKSPACES_VISIBILITY_OPTIONS`
  （`visibleOnFullScreen: true` + `skipTransformProcessType: true`），4 个调用点（`index.ts` OCR 覆盖窗口与
  截图提示窗口、`selectionButton.ts`、`popup.ts`）统一复用；新增回归测试
  `tests/macosWorkspaceWindowVisibility.test.ts` 锁定调用点数量与选项。
- 验证：A/B 脚本采样 `app.dock.isVisible()`，默认选项 dock 由 true 变 false 且不再恢复，加 skip 后恒为 true。

## 修复：OCR 截图时顶部菜单栏与底部 Dock 栏消失

- 现象：按截图快捷键进入 OCR 框选后，菜单栏与 Dock 栏「消失」；微信截图不会（用户反馈）。
- 根因：`openOcrSelection` 在 `win.setBounds(display.bounds)` 之后调用了
  `win.setSimpleFullScreen(true)`（macOS 专用），目的是让 Renderer 的 (0,0) 与 screencapture 快照左上角对齐。
  但**简单全屏会切换 macOS 应用呈现模式并让系统隐藏菜单栏与 Dock 栏**，而采集
  （`captureOcrPreviewSnapshot(display.bounds)`）就发生在进入简单全屏之后 —— 所以快照本身就缺少这两个区域，
  覆盖层背景正是这张快照，用户看到的「消失」是真实缺失，不是遮挡问题。
- 为什么必须绕开：macOS 会把普通无边框窗口钳制在菜单栏下方（`setBounds({y:0})` 实测被抬到 `workArea.y=33`），
  `type:'panel'`、负 y、show 后设层级、panel+全屏 bounds 四种变体实测同样被钳制；简单全屏曾是唯一能盖住菜单栏的方式。
- 修复：OCR 覆盖窗口创建时开启 `enableLargerThanScreen: true`（macOS 专用选项，其它平台忽略），
  实测 `setBounds(display.bounds)` 精确得到 `{0,0,1728,1117}` 且 contentBounds 完全一致、`isSimpleFullScreen() === false`；
  移除 `openOcrSelection` 中的 `setSimpleFullScreen(true)`；`hideOcrSelectionWindow` 里的
  `setSimpleFullScreen(false)` 保留为兜底清理。窗口层级仍是 `screen-saver`(1000) > 菜单栏(24) > Dock(20)，覆盖层正常盖住二者。
- 回归测试：`tests/ocrUiIntegration.test.ts` 新增「应使用 enableLargerThanScreen 而非 macOS 简单全屏」
  「打开流程不应进入 macOS 简单全屏」；`tests/realtimeScreenshotOverlay.test.ts` 把原先要求存在 darwin 分支的断言反转为禁止。
- 副作用：截图区域现在包含菜单栏与 Dock（与微信一致），且不再触发全屏动画/Space 切换。
- 本地流程产物：`openspec/changes/fix-ocr-overlay-menu-bar-dock-hidden/`（proposal / design / tasks / specs）。
  注意 `openspec` 在本机**全局 gitignore**（`~/.gitignore_global:36`）中，所有 change 目录都只是本地文档、不进提交。
- 排查结论：全项目只有 `openOcrSelection` 会把窗口撑到整块显示器；`popup.ts` 与 `selectionButton.ts` 都按
  `display.workArea` 摆放小窗，不存在同类问题。

## 修复：截屏点击复制后设置页自动弹出

- 现象：设置窗口未关闭时，按 OCR 快捷键框选 → 点「复制」→ 覆盖层淡出后**设置页被顶到所有应用最前**。
- 根因（真机脚本实测，非猜测）：OCR 覆盖窗口 `show()+focus()` 会把应用激活成前台应用；它也是应用内最后一个
  key window，`win.hide()` 后 **macOS 会把应用内下一个窗口（设置页）提升为 key window**，而应用仍保持前台，
  于是设置页直接盖住用户原来的应用。**与 `app.on('activate')` 无关**（`shouldTreatActivateAsDockLaunch`
  这条守卫拦不住它）：诊断脚本里 hide 覆盖窗口时根本没有触发 `activate` 事件。
- 验证脚本（`/tmp/diag-activate/`，用 `env -u ELECTRON_RUN_AS_NODE ./node_modules/.bin/electron` 跑）：
  `lsappinfo info -only name $(lsappinfo front)` 采样前台应用名。A=设置窗口（showInactive 模拟「开着但在后台」），
  B=覆盖窗口（show+focus），隐藏 B 后 front 由用户应用变成 Electron、A.isFocused()=true → 复现；
  `app.hide()` + `showInactive(A)` 后 front 回到原应用、A 可见但未聚焦 → 修复成立。
- 修复（`src/main/index.ts`）：`openOcrSelection` 记录 `ocrSessionAppWasFrontmost = BrowserWindow.getFocusedWindow() !== null`
  （应用不在前台时该 API 返回 null，实测确认）；`cancelOcrSelection` 在覆盖窗口原本可见且应用原本不在前台时调用
  新增的 `returnFrontmostToPreviousApplication()` —— 快照当前可见窗口（排除覆盖窗口）→ `app.hide()` 让系统重新
  激活原应用 → 用 `showInactive()` 把窗口恢复成「可见但不抢焦点」，**必须延后**（`app.hide()` 异步生效，
  同一 tick 内 showInactive 会被随后的隐藏动作覆盖，窗口会一直不可见；实测 0ms 的 `setTimeout` 够用，
  这里用 60ms + 180ms 二次校验兜底）。提示胶囊窗口也在这个快照里，所以不会被一起藏掉。
  用 `ocrSelectionSessionSeq` 做会话守卫，避免恢复动作把设置页排到新覆盖窗口之上。
- 回归测试：`tests/ocrFrontRestore.test.ts`（3 条源码接线断言）。`npx tsc --noEmit` 通过；
  `npm test` 1209 用例 / 1207 通过（仍是那两条历史失败）。

## 修复：截屏点击复制后设置页自动弹出（最终方案，取代上一节）

> 上一节记录的两版实现（`showInactive()` 恢复、`app.hide()` + 延迟 `app.show()`）都已被取代，
> 结论保留在下面，避免下次再走一遍弯路。

- 用户复现反馈：「弹出『已复制到剪贴板』后**还是会**弹出设置框」→ 说明第一版 `showInactive()` 恢复无效。
- 为什么 `showInactive()` 是错的：它走 `orderFront`，**会把窗口顶到前台应用之上**。
  真机 z 序采样（`windowz`，`CGWindowListCopyWindowInfo`）：基线「#15 访达 / #16 Electron」，
  `app.hide() + A.showInactive()` 后变成「#15 Electron / #16 访达」——设置页反而盖住了访达。
- 第二版 `app.hide()` + 延迟 `app.show()` 终态是对的（`app.show()` = `unhideWithoutActivation`，
  恢复窗口但不激活应用、不越过前台应用），**但 `app.hide()` 会隐藏应用全部窗口**，
  于是正在展示的「已添加到剪贴板」提示胶囊会闪一下：15ms 间隔采样显示 +44ms 与 +65ms 两帧窗口列表为空。
  实测 `setTimeout(0)` 恢复**无效**（窗口持续离屏约 850ms），`app.show()` 至少需间隔 60ms；
  空档下限约 45ms，调小延迟无法消除。**所以这条路径只作为退化方案保留。**
- 只「先发激活请求再隐藏覆盖窗口」也不够：激活是异步的，同一 tick 内隐藏仍会让设置页被提升，
  实测 +22ms / +54ms 两帧设置页排在访达之前，+74ms 才纠正回来——仍是用户能看见的闪一下。
- **最终方案（`src/main/index.ts`）**：让本应用先失去最前状态，**确认之后再**隐藏覆盖窗口。
  1. `openOcrSelection` 里 `ocrSessionAppWasFrontmost = BrowserWindow.getFocusedWindow() !== null`
     （应用不在前台时该 API 返回 null，实测确认），并在**显示覆盖窗口之前**用
     `readFrontmostAppSnapshot()` 采集「截图前最前的应用」；采集与屏幕采集并发，收尾才 await，不增加覆盖窗口出现延迟。
  2. `readFrontmostAppSnapshot()` 走 `lsappinfo front` + `lsappinfo info <asn>`（约 10~16ms，**不需要任何授权**），
     解析 `bundleID="..."` 与 `pid = N`；`pid === process.pid` 时返回 null（最前就是本应用，强行激活自己反而会把设置页顶到最前）。
  3. `cancelOcrSelection` 在「覆盖窗口原本可见 + 应用原本不在前台」时改调 `returnFrontmostThenHideOcrSelection()`：
     `open -b <bundleId>` 激活截图前的应用 → 每 16ms 轮询 `BrowserWindow.getFocusedWindow() === null`
     （应用失去最前状态后返回 null）→ 确认失活后才 `hideOcrSelectionWindow()`。
     另有 `FRONT_RETURN_TIMEOUT_MS = 200` 的兜底定时器，保证任何情况下覆盖窗口都会被收起，不会留下全屏窗口拦截鼠标。
     退化分支（拿不到目标应用 / 目标已退出 / `open` 失败）先 `hideOverlay()` 再 `restoreAppWindowsByHidingApp()`——
     **顺序不能反**，否则 `app.show()` 会把刚收起的覆盖窗口一起恢复。
  4. 目标应用已退出时必须放弃（`isProcessAlive(pid)`）：否则 `open -b` 会把用户已关闭的应用重新拉起。
- 为什么选「激活原应用」而不是「隐藏自己」：项目里 Windows 侧已有同一语义的先例（`deactivatePopupForCapture`
  主动把前台还给源应用），且只有这条路径能让**所有窗口全程留在屏上**（提示胶囊不闪）。
- 真机验证（`/tmp/diag-activate/e2e-final.cjs` 复刻最终接线，`zsampler` 每 15ms 采样一次 z 序与可见性）：
  48 个样本中 toast **缺席 0 次**、设置页**跑到访达之前 0 次**、覆盖窗口在收尾 +96ms 收起（远小于 200ms 兜底），
  `fallbackFired=false`（主路径生效）。

## 待定：另外两条「隐藏覆盖窗口」路径存在同类现象（已测出证据，未改）

- 影响面：`failOcrSelectionCapture`（采集失败弹错误弹窗）与 `submitOcrSelection`（框选后识别翻译弹弹窗），
  两者都是**先** `hideOcrSelectionWindow()`、**再** `showPopup(...)`，而 `showPopup` 的 `activate` 默认 `true`
  （`win.show()` 激活应用）→ 覆盖窗口隐藏的瞬间应用仍是前台应用，设置页被提升为 key window 顶到访达之前。
- 真机实测（`/tmp/diag-activate/popupflow.cjs`，设置页 + floating 弹窗 + 全屏覆盖窗口）：
  - 变体 A（当前实现：先隐藏覆盖窗口、再显示弹窗）→ 收尾后 `#16 Electron(设置页)` 排在 `#17 访达` **之前**（错误）。
  - 变体 B（先显示弹窗、再隐藏覆盖窗口）→ `#16 访达` / `#17 Electron(设置页)`（正确），弹窗仍在最上。
  - 机制：**激活应用只会把 key window 抬到最前**（变体 B 里设置页在访达之后即证据），
    设置页被顶到最前是因为它「被提升为 key window」；先让弹窗接管 key window，就不会再发生提升。
- 变体 B 的安全性已验证（`/tmp/diag-activate/popupblur.cjs`）：弹窗显示后 `P.isFocused=true`，
  隐藏覆盖窗口后仍 `isFocused=true`、`blurCount=0`，**不会被 `handlePopupBlur` 误关闭**。
- 为什么没有直接改：`popup.ts` 里 `foregroundTracker.remember()` 在 **Windows 上依赖「覆盖窗口已隐藏、源应用已回到前台」**
  这一时序（`createWindowsForegroundTracker` 非 win32 平台是空操作），因此重排只能 **macOS 专属**，
  Windows 必须保持原顺序。改动落在应用主流程（截图翻译）上，且无法在本机验证 Windows，故留待用户确认后再动。
- 另注：`submitOcrSelection` 的 `!bounds` 早退分支没有弹窗接管 key window，同属此类。

## 修复：设置页开着时「划词」取词失败会把设置页顶到最前

- 现象：设置窗口未关闭（但在后台）时，用选区旁「译」按钮划词，**取词失败**会同时把设置页顶到所有
  应用最前；取词成功与快捷键取词都不复现。
- 根因（真机对照实验，非猜测）：`handleSelectionCaptureResult` 的 `!result.text` 失败分支调用
  `showPopup(..., 2000, anchor)` 时**未传 `activate=false`**，走了默认 `win.show()`：
  这一步让本应用成为前台应用，失败提示成为应用内 key window。
  2 秒后 `hidePopup()` → `handBackFrontmostThen()`：当 `pendingReturnApp` 为空时（按钮路径常见，
  记录是异步 `lsappinfo` 读取，取词失败返回太快 / 上一轮已消费）落到「无可用源应用目标」退化分支
  ——不交还前台直接 `win.hide()`，macOS 便把应用内下一个窗口（设置页）提升为 key window 顶到最前。
  快捷键路径因为同步流程里 `pendingReturnApp` 已记录并成功交还，所以不复现。
- 对照实验（`/tmp/diag-fail/compare.cjs`）：
  - 场景 B（`pending=null` + 失败弹窗 `activate=true`）→ 收尾后设置页排在访达**之前**（BUG 复现）。
  - 场景 C（失败弹窗保持非激活）→ handBack 入口 `focused=null` → 设置页在访达**之后**（正确）。
  - 另测：点击 `focusable:false` 的「译」按钮不会激活本应用；`activate` 事件数为 0，与
    `app.on('activate')` 守卫无关，纯窗口层级机制。
- 修复（macOS 专属）：
  - `src/shared/popupForeground.ts` 新增 `shouldActivatePopupForCaptureFailure(platform)`：
    `darwin` 返回 false，其余平台返回 true。
  - `src/main/index.ts` 的取词失败提示改传该策略作为 `showPopup` 第 4 个参数。
    macOS 上以 `showInactive()` 显示提示：提示仍在最上可见、2 秒后自动隐藏，但中途不会把本应用
    变成前台应用，收尾时 `handBackFrontmostThen` 走「已不在最前」安全分支，不隐藏 key window 语义。
    Windows/Linux 保持原有激活行为，不影响取词焦点时序。
- 回归测试：`tests/popupFrontRestore.test.ts` 新增 1 条（平台策略 + 失败分支接线断言）。
  `npx tsc --noEmit` 通过；`npm test` 1226 用例 / 1224 通过（仍是那两条历史失败：
  `aiIpcContract` 正则失配、`updateRangeDownload` 偶发超时）。
